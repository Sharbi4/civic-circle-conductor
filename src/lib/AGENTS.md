# Connector status notes
- LinkedIn profile photos travel with the encrypted owner-scoped connection and only their safe display URL enters connection status; account avatars share that refreshed status without replacing organization letterhead logos.
- X status reads the authenticated member photo through the owner's stored connection; shared account avatars prefer LinkedIn then X, while X's connector row always uses its own photo. Cache status reads for five minutes and invalidate on connection changes to avoid unnecessary provider calls.
- Eventbrite status retrieves only the authenticated member image (expanded image or its media ID) with the owner's encrypted token; its connector avatar is independent, and shared avatars use it after LinkedIn and X. Never substitute an event cover or organization logo for a member photo.

# Chat, research and event page notes
- Automatic instruction turns (research hand-backs, plan steps, resumes, scheduled runs) are saved as role 'system' via runOrganizer({hidden:true}) and filtered by isHiddenTurn; why: the model needs them but the organizer must never see them as their own messages.
- Browser-opened PDFs/Word files are read server-side (unpdf/fflate, falling back to an in-page fetch) and their facts plus event conflicts are stored as step notes; why: the browser shows no text for documents and booking facts live in them.
- Research results reach the event page through event_venue/event_contact/event_vendor markers parsed by eventPage.shared and merged (never un-booking) by eventPage.server, from both chat replies and browser summaries; why: the event page must reflect what research found.
- The live browser keeps one 'page' step note per visited non-search page (model page_notes, else price/contact lines from the full page text); notes don't count toward the step limit; why: summaries must still have each vendor's prices and contacts after the browser moves on.
- Vendor comparison tables and venue phone/email are parsed into event-page vendors and Contacts alongside markers; research conflicts hand back with alternatives-first instructions instead of the call fallback; why: models emit markers inconsistently and a conflict needs a new plan, not an exception call.
- The chat's live browser card asks Browserbase (checkBrowserSession) whether the session is open on load, every 30s and on tab focus; closed/404 sessions are marked ended, unreachable checks never end them, and the iframe waits for the first answer; why: Browserbase closes sessions on its own and a stale debugger URL renders a raw DevTools error.

# Scheduling and step states
- Managed schedules (scheduler, recovery, reports) only hand their job to Inngest (startSharedJob → /api/public/inngest) and answer at once, because their HTTP call is cut off after ~5 seconds; a failed hand-off returns 502 instead of running inline (which would be cut off holding the job lock), and an Inngest backup cron 7 minutes later runs the scheduler only if it hasn't finished recently. Inngest is registered against the stable project--<id>.lovable.app origin (custom domains can briefly serve an older version after publishing). In Inngest the job does its bookkeeping, closes quiet reviews in SQL and wakes only organizations with queued runs or an unattended driving browser; each wake is bounded, retries are off and every step is its own request, so unknown outcomes go to review and idle organizations cost nothing. The open app still runs its own due work (runOwnerDueWork); database claims and browser leases keep the two from doubling up.
- Steps park in waiting_on / on_hold / your_pick / awaiting_reply via Civi's [[step_status]] marker or inferStepStatus on its reply; failed, interrupted and declined steps never replay on their own, only on a reply or a step button, so unchanged steps aren't re-run.
- Step times, follow-ups and "today" use the organization's time_zone (zonedTime.shared), never a fixed zone.
- New chats reuse a browser only after reusableBrowser confirms the provider still has it open; closed ones are marked ended so tasks open a fresh browser.

# Writing style
- Every model call adds the shared punctuation rule via withNoDashes and every model text output passes noLongDashes; chat, document, step and approval displays also run noLongDashes so older saved text matches. Internal note formats that code parses (page notes, document "Read" notes) keep their separators.
